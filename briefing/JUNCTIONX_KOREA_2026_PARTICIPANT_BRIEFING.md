## 1. 한 페이지 요약

### 이 대회의 본질

JUNCTIONX Korea는 단순히 아이디어를 많이 내거나 기능 수를 경쟁하는 행사가 아니다. **파트너가 제시한 현실의 문제를 48시간 안에 해석하고, 사용자 가치와 기술 가능성을 실제로 작동하는 프로토타입으로 증명하는 파트너 주도형 오픈 이노베이션 해커톤**에 가깝다.

공식 한국 행사에서 강조하는 세 단어도 같은 흐름을 가리킨다.

- **BREAK**: 익숙한 전제·한계·해결 방식을 해체한다.
- **REBUILD**: 기술·아이디어·사람을 새롭게 연결해 해결책을 구현한다.
- **IMAGINE**: 아직 존재하지 않는 경험을 작동하는 형태로 보여준다.

근거: [JUNCTIONX Korea 2026 공식 사이트](https://asia.hackjunction.com/)

### 운영진과 트랙 파트너가 보고 싶은 것

한국 대회의 세부 심사표는 아직 공개되지 않았다. 다만 Junction 공식 약관, 글로벌 파트너 자료, 다른 Junction 대회의 공식 기준을 종합하면 다음 여섯 항목이 반복된다.

1. **트랙 적합성** — 제시된 문제에 정확히 답하는가
2. **새로움** — 익숙한 기능의 조합을 넘어 새로운 관점이 있는가
3. **기술적 완성도** — 핵심 기술이 실제로 작동하며 설명 가능한가
4. **사용자 경험** — 누가 왜 쓰는지, 핵심 흐름이 명확한가
5. **데모 가능성** — 48시간 결과를 직접 보여줄 수 있는가
6. **실현 가능성과 영향** — 행사 뒤에도 발전시킬 이유와 경로가 있는가

여기에 기술/API 중심 트랙이라면 **파트너 기술을 장식이 아니라 핵심 가치에 제대로 사용했는가**가 추가될 가능성이 높다.

근거: [Junction 이용약관](https://www.hackjunction.com/terms-of-service), [Junction 파트너 안내](https://www.hackjunction.com/partners)

### 가장 중요한 승리 조건

> 한 문장으로 설명되는 사용자 문제 + 처음부터 끝까지 작동하는 핵심 흐름 하나 + 그것이 가치 있다는 증거 + 실패하지 않는 데모

기능 다섯 개가 반쯤 작동하는 것보다, 사용자의 변화가 보이는 한 흐름이 안정적으로 작동하는 편이 강하다. 발표 자료는 데모를 대신하는 것이 아니라 데모의 의미를 설명해야 한다.

### 고기범에게 맞는 포지션

고기범의 경쟁력은 `SwiftUI 개발자`라는 한 단어보다 넓다.

- iOS·iPadOS·macOS·watchOS 인터페이스를 빠르게 만든다.
- REST API·AI/LLM API·로컬 상태를 연결할 수 있다.
- CoreBluetooth·ESP32·ESP-NOW·센서·액추에이터를 앱과 연결할 수 있다.
- 불확실한 시스템을 단계별 실험으로 나누고 실제 기기에서 검증한다.
- AI Agent와 Worktree를 이용해 탐색·구현·검증 작업을 분기할 수 있다.

따라서 맡아야 할 역할은 **팀의 아이디어를 End-to-End 데모로 연결하고, 가장 위험한 기술 가정을 초반에 제거하는 Product-minded Developer**다.

단, 강한 기술을 모두 쓰는 것이 목표는 아니다. 트랙 문제에 필요하지 않다면 BLE·하드웨어·Apple Watch를 과감히 버릴 수 있어야 한다.

## 4. 이 대회가 참가자에게 실제로 원하는 것

### 4.1 트랙 문제를 정확히 읽는 능력

많은 팀이 트랙 발표를 듣자마자 자신이 만들고 싶은 앱에 문제를 끼워 맞춘다. 파트너가 원하는 것은 일반적인 좋은 아이디어가 아니라 **자신들이 제시한 문제의 제약을 이해한 프로토타입**이다.

트랙 설명에서 다음 여섯 문장을 뽑아야 한다.

1. 실제 사용자는 누구인가?
2. 사용자의 현재 행동에서 무엇이 깨져 있는가?
3. 파트너는 어떤 결과가 달라지기를 원하는가?
4. 반드시 사용해야 하는 데이터·API·기술이 있는가?
5. 심사 기준과 가중치는 무엇인가?
6. 48시간 뒤 무엇을 직접 보여주면 성공인가?

### 4.2 문제 중심 트랙과 기술 중심 트랙을 구분하는 능력

글로벌 Junction 자료는 Challenge를 크게 두 성격으로 설명한다.

- **문제 중심**: 현실 문제를 새롭게 해결하는 것이 핵심이다. 기술 선택은 해결책에 종속된다.
- **기술 중심**: 파트너의 플랫폼·API·도구를 의미 있게 사용해 채택 가능성을 보여주는 것이 핵심이다.

이는 Korea의 세 트랙을 공식적으로 분류한 명칭이 아니라 트랙 의도를 읽기 위한 분석 프레임이다. 문제 중심 트랙에서 특정 기술을 억지로 쓰면 사용자 가치가 약해지고, 기술 중심 트랙에서 파트너 API를 주변 기능에만 쓰면 트랙 적합성이 약해진다. 트랙 공개 후 어느 유형인지 먼저 합의해야 한다.

### 4.3 아이디어가 아니라 검증 가능한 주장

강한 프로젝트는 “AI로 해결한다”가 아니라 다음처럼 말할 수 있다.

> `[사용자]`가 `[상황]`에서 겪는 `[구체적 문제]`를, `[핵심 메커니즘]`으로 줄인다. 48시간 동안 `[작동하는 행동/지표]`로 이를 검증한다.

예:

- 약한 주장: “AI로 현장 안전을 혁신한다.”
- 강한 주장: “지휘자가 동시에 관리해야 하는 대원 중 응답이 끊긴 사람을 놓치지 않도록, 상태 전환과 마지막 연결 시각을 한 화면에서 구분하고 시나리오 테스트로 식별 시간을 측정한다.”

### 4.4 기술을 끝까지 연결하는 능력

Junction 공식 자료가 강조하는 결과물은 설명서가 아니라 **프로토타입**이다. 화면만 있는 Figma, API만 있는 서버, 센서만 읽는 펌웨어는 각각 부분 결과다.

평가자가 보고 싶은 흐름은 다음과 같다.

```text
사용자 입력/상황
→ 핵심 처리
→ 파트너 기술 또는 팀의 차별화 로직
→ 사용자가 이해할 수 있는 결과
→ 다음 행동 또는 상태 변화
```

모든 기능을 완성하지 못해도 이 한 줄은 실제로 연결되어야 한다.

### 4.5 피드백을 빠르게 흡수하는 능력

파트너 피드백이 9시간 배정되어 있다는 것은 멘토링이 부가 행사라는 뜻이 아니다. 트랙 의도를 잘못 읽은 팀을 교정하고, 파트너가 중요하게 보는 기준을 직접 얻는 핵심 구간이다.

좋은 팀은 “아이디어가 어떤가요?”보다 아래처럼 질문한다.

- 저희가 정의한 사용자가 파트너가 생각한 실제 사용자와 일치합니까?
- 이 문제에서 절대 무시하면 안 되는 운영 제약은 무엇입니까?
- 정확도와 속도, 새로움과 완성도 중 어느 쪽을 더 높게 평가합니까?
- 이 API를 사용했다는 사실보다 어떤 활용 결과를 보고 싶습니까?
- Mock Data·수동 확인·외부 모델 사용은 어디까지 허용됩니까?
- 기술적으로 멋져도 트랙 취지에서 벗어났다고 판단할 사례는 무엇입니까?

### 4.6 범위를 줄이고 마감하는 능력

48시간의 실질 구현 시간은 개막·워크숍·식사·피드백·제출·Expo 준비를 빼면 더 짧다. 공식 일정상 트랙 공개에서 최종 제출까지는 약 40시간이다.

따라서 기능을 세 등급으로 나눈다.

| 등급 | 정의 | 원칙 |
|---|---|---|
| Must | 이것이 없으면 사용자 가치가 증명되지 않음 | 첫날 밤부터 End-to-End로 연결 |
| Should | 핵심 흐름을 더 이해하기 쉽거나 신뢰하게 만듦 | Must가 세 번 연속 재현된 뒤 추가 |
| Could | 있으면 멋있지만 결과의 본질은 바뀌지 않음 | 발표 전까지 구현 금지에 가깝게 관리 |

### 4.7 결과의 한계를 정직하게 설명하는 능력

특히 AI·의료·안전·금융·하드웨어 프로젝트는 48시간 프로토타입을 실제 서비스 수준으로 과장하면 신뢰를 잃는다.

- 검증한 데이터와 Mock Data를 구분한다.
- 실제 모델 출력과 하드코딩된 데모를 구분한다.
- 자동화된 단계와 사람이 확인하는 단계를 구분한다.
- 정확도·거리·성능을 측정하지 않았다면 단정하지 않는다.
- 행사 뒤 검증해야 할 위험을 한 문장으로 밝힌다.

이 정직함은 약점 고백이 아니라 기술적 판단력의 증거다.

## 6. 팀 구성 전략

### 권장되는 보완 관계

최대 4명이라면 다음 능력이 모두 존재하도록 구성하는 편이 좋다. 역할 이름보다 실제 행동 가능 여부가 중요하며 한 사람이 두 역할을 겸할 수 있다.

| 필요 능력 | 행사 중 책임 |
|---|---|
| Product/Story | 트랙 해석, 파트너 질문, 범위, 일정, 발표 논리 |
| Design/UX | 사용자 흐름, 정보 위계, Figma, 데모의 이해 가능성 |
| Client/System Integration | 사용자 인터페이스, 상태 흐름, 기능 통합, 실제 데모 |
| Backend/Data/AI | API, 데이터 처리, 모델, 배포 또는 로컬 서비스 |

고기범은 세 번째 역할을 중심으로 첫 번째 역할의 일부까지 맡을 수 있다. 따라서 우선적으로 찾을 사람은 다음과 같다.

1. 빠른 Backend·Data·배포가 가능한 개발자
2. 사용자 흐름과 시각 전달이 강한 디자이너
3. 파트너 질의, 영어 피치, 시간 관리를 주도하는 제품형 팀원

### 팀원을 선택할 때 기술 스택보다 볼 것

- 모르는 것을 빠르게 인정하고 작은 실험으로 바꾸는가
- 자신의 작업 상태를 `완료/부분 완료/미검증`으로 구분하는가
- 상대의 작업을 기다리지 않고 Mock으로 인터페이스를 맞출 수 있는가
- 아이디어에 반대해도 사람을 공격하지 않는가
- 발표와 제출 같은 비개발 작업도 팀의 일로 보는가
- 밤샘을 열정의 증거로 여기지 않고 교대 휴식을 받아들이는가

### 혼자 또는 2인으로 남았을 때

최소 인원 제한은 없지만, Demo Expo와 Final Pitch까지 고려하면 혼자서 제품·발표·제출을 모두 관리하는 위험이 크다. 팀을 구하지 못했다면 제품 범위를 더 좁히고, 최소한 발표·디자인 피드백을 주고받을 동료를 행사장에서 확보한다.

### 7.4 마지막 10분: Kill Criterion을 정한다

가장 위험한 기술 가정마다 제한 시간을 둔다.

예:

- 90분 안에 파트너 API의 실제 응답을 받지 못하면 Mock Data로 전환
- 120분 안에 Watch와 Phone의 핵심 데이터 교환이 안 되면 단일 기기로 축소
- 60분 안에 모델 출력이 정해진 Schema를 안정적으로 지키지 못하면 규칙 기반 후처리 또는 사람 확인 단계 추가
- 외부 서비스의 이용약관이 불명확하면 해당 데이터 사용 중단

이 기준은 포기를 쉽게 하기 위한 것이 아니라 팀 전체가 한 막힌 기술에 끌려가지 않게 한다.

## 8. 파트너 워크숍에서 반드시 물을 질문

5. 공식 심사 항목과 가중치는 어떻게 됩니까?

## 10. 개발·통합 운영 원칙

### 10.1 먼저 데이터 계약을 합의한다

Frontend와 Backend가 따로 완성되는 것을 막으려면 첫날 밤에 다음을 정한다.

- 입력 예시
- 출력 예시
- 필수·선택 Field
- 오류 상태
- 누가 Source of Truth를 가지는가
- Mock과 실제 응답을 바꾸는 위치

### 10.2 완료를 네 단계로 구분한다

```text
코드 작성됨
→ 로컬에서 동작함
→ 다른 파트와 통합됨
→ 발표 환경에서 반복 재현됨
```

`완료`라는 말 대신 현재 단계를 말한다.

### 10.3 AI Agent와 Worktree는 독립성이 있을 때만 쓴다

고기범은 긴 맥락을 Obsidian 노드로 구조화하고, 작업을 새 세션·Worktree로 분기해 리소스를 배분하는 방식에 익숙하다. 이것은 해커톤에서도 강점이 될 수 있지만, 팀의 Git 숙련도와 통합 비용을 고려해야 한다.

권장 사용법:

- API 조사, Mock 작성, 테스트 생성, README 초안처럼 입력·출력이 명확한 일은 AI Agent에 분리한다.
- 서로 다른 화면이나 독립 모듈은 Worktree/Branch로 격리할 수 있다.
- 핵심 Architecture와 데이터 계약, 최종 Merge는 통합 담당자가 직접 검토한다.
- 2–3시간마다 Main 흐름에 합치고 오래 살아 있는 Branch를 만들지 않는다.
- 맥락이 길어지면 `결정 / 근거 / 현재 상태 / 미해결 위험 / 다음 행동`만 새 노드에 남긴다.
- 파트너 비공개 정보와 개인정보를 외부 AI에 보내지 않는다.

팀이 Worktree를 처음 접한다면 행사 중에 강요하지 않는다. 단순 Branch와 짧은 통합 주기가 더 안전할 수 있다.

### 10.4 기술별 핵심 위험

#### AI/LLM

- Demo 입력을 외워 답하는 것처럼 보이지 않게 여러 입력을 시험한다.
- JSON Schema·Retry·Timeout·Fallback을 둔다.
- 모델이 만든 설명과 공식 데이터 조회 결과를 구분한다.
- 정확도를 측정하지 않았다면 ‘정확하다’고 말하지 않는다.
- AI가 꼭 필요한 이유가 없으면 규칙 기반 방식과 비교한다.

#### 외부 API·Cloud

- Rate Limit과 결제 한도를 확인한다.
- 로컬 Mock·Cache를 준비한다.
- 인증 Token 만료와 네트워크 실패를 데모 전에 시험한다.
- 무료 Tier와 행사 후 운영 비용을 설명할 수 있게 한다.

#### BLE·Hardware

- 첫 실험은 `발견 → 연결 → 1개 명령 → 1개 상태`까지만 한다.
- 여러 기기로 늘리기 전에 한 대를 반복 재현한다.
- 배터리, 케이블, 포트, Driver와 페어링 초기화 방법을 문서화한다.
- 물리 장치가 실패해도 앱·Recorded Demo로 핵심 가치를 설명할 수 있게 한다.

#### Apple Platform

- 실제 기기의 Developer Mode, Signing과 Provisioning을 행사 전에 확인한다.
- TestFlight 배포 시간에 의존하지 않는다.
- 화면 미러링·Stage Manager·외부 디스플레이를 미리 시험한다.
- 특정 Apple 기기가 없으면 팀원과 심사자가 경험할 방법을 준비한다.

## 11. 데모와 발표 설계

### 11.1 6장 발표 자료

1. **Problem** — 누구의 어떤 순간이 깨져 있는가
2. **Insight** — 기존 방식이 왜 해결하지 못했는가
3. **Solution** — 한 문장 가치와 핵심 흐름
4. **Live Demo** — 사용자의 전후 변화
5. **How & Proof** — 기술 구조, 파트너 기술, 사용·테스트 근거
6. **Next** — 한계, 다음 검증, 행사 뒤 확장

별도의 팀 소개·기술 스택 장표를 길게 두지 않는다. 역할과 기술은 제품을 설명하는 데 필요한 순간에만 넣는다.

### 11.2 데모에서 보여야 할 것

- 사용자의 시작 상태
- 핵심 입력 한 번
- 시스템의 차별화된 처리
- 사용자가 이해할 수 있는 결과
- 결과 때문에 달라지는 다음 행동

### 11.3 근거로 사용할 수 있는 것

- 행사 참가자 5–10명의 간단한 사용 관찰
- 동일 시나리오의 반복 성공 횟수
- 이전 방식 대비 단계·시간 감소
- API 응답 시간과 실패율
- 모델 출력 Schema 통과율
- 파트너 피드백 전후 변경 사항
- 실제 기기 영상·로그·측정값

표본이 작다면 ‘효과가 입증됐다’가 아니라 ‘이 가설을 지지하는 초기 신호를 얻었다’고 표현한다.

### 11.4 백업 체계

- 실제 데이터가 실패할 때 로컬 Mock
- 네트워크 없이 작동하는 최소 경로
- 자동화가 실패할 때 사용자 확인 단계
- 정상 동작을 촬영한 30–60초 영상
- PDF로 Export한 Deck
- 발표 기기 외 두 번째 실행 기기 또는 빌드 복사본
- 제출 담당자와 대체 담당자

백업 영상은 Live Demo를 포기하기 위한 것이 아니라 실패했을 때 발표의 논리를 보존하기 위한 보험이다.

## 12. 과거 Junction 사례에서 배울 것

과거 사례는 2026 규칙이 아니라 행동 전략의 근거다.

### 12.1 2022 Junction Asia 우승팀: 맞지 않는 트랙을 버리고 실제 사용 증거를 만들었다

한 우승 회고에 따르면 팀은 처음 선택한 트랙에서 몇 시간을 작업한 뒤 재미와 우승 가능성이 모두 낮다고 판단해 새벽에 다른 트랙으로 전환했다. 새 문제에서는 빠르게 Product/ML PoC를 만들고, 마감 약 2시간 전 참가자들에게 공개해 **118명·1,160회 플레이**라는 초기 사용 데이터를 발표에 활용했다.

이 사례의 교훈은 ‘늦게라도 무조건 Pivot하라’가 아니다.

- 이미 쓴 시간보다 남은 시간의 승산을 본다.
- 심사위원이 중요하게 보는 것을 다시 읽는다.
- 주장 대신 작은 실제 사용 증거를 만든다.
- 팀 안에서 직접적이고 논리적인 피드백을 허용한다.

출처: [Junction Asia 2022 우승 회고](https://blog.kshgroup.kr/junction-asia-2022-review/), [Junction Asia 2023 공식 우승자 인터뷰](https://medium.com/@junctionasia_2023/we-are-the-winner-of-junction-fd91c3aa475b)

### 12.2 2021 참가 회고: 제출 시각은 제품 기능만큼 중요하다

과거 참가자는 예상보다 이른 제출 마감 때문에 거의 제출을 놓칠 뻔했다고 기록했다. 2026에도 Mission 1이 트랙 공개 4시간, 워크숍 종료 2시간 뒤에 온다.

교훈:

- 공식 시각보다 내부 마감을 앞당긴다.
- 제출 담당자를 한 명 지정한다.
- 최종 시간에 Build·Upload·권한 설정을 처음 하지 않는다.

출처: [JunctionX Seoul 2021 참가 회고](https://roseline.oopy.io/dev/hackathon-2021-junction-x-seoul-korean)

### 12.3 과거 공식 결과: 기술에 사람의 맥락을 더한 팀이 보였다

부산시의 2023 공식 결과 자료는 수상작들이 주방·관광·주거 공유·음식 배달 같은 문제를 다루며 기술에 혁신성과 사람 중심 관점을 더했다고 설명한다. 2026의 심사 기준을 뜻하지는 않지만, Junction Asia가 단순 기술 시연보다 현실 맥락이 있는 제품을 선호해 왔다는 참고 사례다.

### 12.4 해커톤 연구: 강한 팀은 발산과 수렴을 반복한다

## 13. 고기범 맞춤 전략

### 13.1 역할 정의

추천 역할명은 다음과 같다.

> **Client & System Integration Developer — 사용자의 핵심 행동을 SwiftUI로 빠르게 구현하고, API·AI·센서·디바이스 중 필요한 요소를 연결해 반복 가능한 End-to-End 데모를 책임지는 개발자**

### 13.2 강점을 사용하는 순서

1. **문제 해석** — 사용자, 입력, 상태 변화, 실패 조건을 구조화한다.
2. **위험 제거** — API/모델/통신/센서 중 가장 불확실한 연결을 최소 코드로 확인한다.
3. **Vertical Slice** — 임시 UI와 Mock을 써서라도 입력에서 결과까지 연결한다.
4. **제품화** — SwiftUI 상태 흐름과 오류·로딩·재시도를 다듬는다.
5. **통합·검증** — 실제 기기와 데이터로 반복하며 로그와 백업을 남긴다.
6. **설명** — 구현한 것, 가정한 것, 다음 검증을 구분해 발표한다.

### 13.3 Apple·Hardware를 선택할 조건

다음 네 질문 중 하나라도 답이 약하면 하드웨어를 중심에 두지 않는다.

- 물리적 입력·웨어러블·다중 기기가 사용자의 실제 문제를 더 잘 해결하는가?
- 40시간 안에 실제 기기에서 반복 가능한가?
- 평가자가 30초 안에 물리적 구현의 가치를 이해하는가?
- 장치가 실패해도 앱 단독 또는 영상으로 핵심 가치를 보존하는가?

사용 조건이 맞으면 고기범의 경험은 강한 시각적·기술적 차별점이 된다. 조건이 맞지 않으면 SwiftUI의 빠른 제품 구현과 통합 능력만 쓰는 편이 낫다.

### 13.4 가져갈 최소 기술 키트

#### 필수

- MacBook, 충전기, 멀티포트 Hub, HDMI/USB-C Adapter
- 실제 iPhone/iPad, 데이터 케이블, 예비 충전기
- Apple Developer 로그인과 Signing이 확인된 빈 SwiftUI 프로젝트
- REST·Codable·Mock Repository·Error State 최소 코드
- Screen Recording과 Demo Build 절차
- Python 기반 데이터 확인·간단한 자동화 환경

#### 트랙에 맞을 때만

- XIAO ESP32-C6 또는 익숙한 ESP32 보드 1–2대
- 신뢰하는 USB 데이터 케이블 여러 개
- 최소 센서·LED·진동 모터와 배선
- CoreBluetooth 최소 왕복 예제
- Embedded Swift 또는 Arduino Toolchain 중 행사에서 더 안정적인 것

새로운 보드와 Toolchain을 현장에서 처음 사용하지 않는다. 기술적 새로움보다 재현성이 우선이다.

### 13.5 AI·Obsidian·Worktree 운영

고기범의 AI 활용은 코드 자동 생성보다 **맥락과 리소스를 나눠 병렬로 탐색한 뒤 다시 통합하는 방식**에 강점이 있다.

행사에서는 다음처럼 제한적으로 사용한다.

- 메인 노드: 문제, 심사 기준, 현재 결정, 핵심 위험, 제출 필드
- 조사 Agent: 파트너 API·문서·라이선스
- 구현 Agent: 작은 독립 모듈 또는 Mock
- 검증 Agent: Test Case, Edge Case, Demo Checklist
- 문서 Agent: README·발표 문구의 초안

한 세션의 맥락이 길어지면 모든 대화를 들고 가지 않고 `결정된 것 / 검증된 것 / 버린 것 / 남은 질문`으로 구조화한 뒤 새 세션으로 분기한다. 다만 팀이 보지 못하는 개인 지식 시스템이 의사결정의 단일 진실이 되지 않도록, 최종 결정은 짧은 공유 문서에 동기화한다.

### 13.6 피해야 할 개인적 함정

- 구현 가능성이 보인다는 이유로 범위를 계속 넓히기
- BLE·Watch·AI를 사용할 수 있다는 이유로 문제에 끼워 넣기
- 혼자 디버깅을 오래 하다가 팀 공유가 늦어지기
- 아키텍처의 안정성을 올리느라 사용자 흐름을 늦게 연결하기
- AI Agent와 Worktree를 과도하게 늘려 통합 비용을 키우기
- 기술적 설명을 길게 해 핵심 결정이 묻히게 하기

대응 문장:

> “지금 하는 일이 이번 트랙의 핵심 사용자 흐름과 12시 제출을 직접 지키는가?”

답이 아니면 멈추거나 이후 항목으로 내린다.

## 18. 최종 성공 기준

수상은 통제할 수 없지만 다음은 통제할 수 있다.

- 트랙 문제와 파트너 의도를 한 문장으로 설명한다.
- 가장 위험한 가정을 첫날 밤에 검증한다.
- 한 가지 사용자 흐름이 실제로 처음부터 끝까지 작동한다.
- 심사 기준과 파트너 피드백이 제품 선택에 반영되어 있다.
- Demo가 세 번 연속 재현되고 실패 시 백업이 있다.
- 구현한 것과 가정·Mock·한계를 구분한다.
- 제출을 내부 마감 안에 끝낸다.
- 팀이 48시간의 결정과 배움을 행사 뒤에도 설명할 수 있다.

> **핵심 전략:** 정답을 미리 만들지 않는다. 문제 공개 후 두 시간 안에 파트너 의도와 핵심 가설을 정리하고, 남은 시간에는 기능을 늘리기보다 그 가설을 가장 짧고 안정적인 데모로 증명한다.
