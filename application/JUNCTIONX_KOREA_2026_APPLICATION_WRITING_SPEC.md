# JUNCTIONX Korea 2026 지원서 직접 작성 명세서

> 목적: 고기범 본인이 지원서를 직접 작성할 때 사용할 내용·구조·사실 검증 기준  
> 이 문서는 제출용 답안이 아니다. 문항별로 무엇을 넣고 뺄지 판단하기 위한 설계 문서다.

## 1. 전체 작성 목표

지원서 전체를 읽은 사람이 다음 네 가지를 분명히 이해할 수 있어야 한다.

1. 어떤 개발자인가?
   - SwiftUI 앱과 임베디드 디바이스를 연결할 수 있다.
   - 화면 안의 기능보다 전체 사용자 경험과 시스템 흐름을 본다.
2. 실제로 무엇을 해봤는가?
   - DanceOrFreeze 팀 프로젝트
   - Embedded-Swift-Xcode-Template 오픈소스
   - RIT 커맨드보드 기획
   - SCPC AI Agent Harness 분석
3. 팀에서 어떤 역할을 할 수 있는가?
   - 추상적인 아이디어를 구현 단위로 나눈다.
   - 위험한 기술 가설을 먼저 검증한다.
   - 앱·통신·디바이스를 End-to-End로 연결한다.
4. 왜 JunctionX가 필요한가?
   - 이미 가진 기술을 자랑하기 위해서만 지원하는 것이 아니다.
   - 낯선 문제, 처음 만난 팀과 48시간이라는 제한 속에서 선택하고 완성하는 능력을 시험하려 한다.

지원서 전체의 중심 문장은 다음 방향이어야 한다.

> 나는 모바일 앱과 물리적 디바이스를 연결해 아이디어를 실제로 작동시키는 개발자이며, JunctionX에서는 팀의 가장 중요한 가설을 제한된 시간 안에 검증 가능한 MVP로 완성하고 싶다.

이 문장을 그대로 제출할 필요는 없다. 다만 각 문항이 서로 다른 방향으로 흩어지지 않도록 기준으로 사용한다.

## 2. 전체 문체 명세

### 반드시 지킬 것

- 본인이 실제로 말할 수 있는 어휘를 사용한다.
- 한 문장에 하나의 핵심 주장만 둔다.
- 추상적인 장점 뒤에는 실제 행동이나 결과를 붙인다.
- 기술명은 역량을 증명하는 데 필요한 만큼만 사용한다.
- 팀 프로젝트는 `내가 했다`와 `팀이 했다`를 구분한다.
- 현재 진행 중인 일과 완료된 결과를 구분한다.
- 확인된 사실과 개인적인 해석을 구분한다.
- 실패나 한계도 숨기지 않되, 배운 행동 변화까지 연결한다.

### 피해야 할 문체

- 지나치게 완벽한 자기소개서 문체
- 모든 문장이 교훈이나 명언으로 끝나는 문체
- `열정`, `혁신`, `성장`, `도전` 같은 단어만 반복하는 문체
- 실제 장면 없이 “저는 협업을 잘합니다”라고 선언하는 문체
- 영어 기술 용어를 과도하게 섞는 문체
- 기업 홍보 문구처럼 Junction의 가치를 그대로 반복하는 문체
- 본인이 평소 사용하지 않는 과장된 감정 표현
- AI가 만든 문장처럼 동일한 길이와 리듬이 반복되는 문체

### 권장 문장 패턴

다음 순서를 자주 활용한다.

```text
처음에는 A라고 생각했다.
실제로 B를 확인하면서 그 가정이 부족하다는 것을 알았다.
그래서 C를 했다.
그 결과 D를 확인했다.
이후에는 E를 먼저 확인하는 방식으로 바뀌었다.
```

다음과 같은 근거 연결도 유용하다.

```text
저는 시스템의 전체 흐름을 보는 편입니다.
DanceOrFreeze에서 iPad, BLE Hub와 참가자 디바이스 사이의 명령·상태 흐름을 연결한 경험이 그 예입니다.
```

  - 설치 스크립트
  - SwiftUI 설치 도구
  - ESP32-C6 NeoPixel 예제

- 아키텍처 판단, 디버깅과 하드웨어 검증을 작성자가 담당했다고 README에 명시

- RIT 커맨드보드의 현재 방향:
  - iPad 기반 지휘 보조 시스템
  - 퇴출 명령 이후 응답·연결·복귀 상태 구분

  - 안전장비를 대체한다고 주장하지 않음
- SCPC AI Challenge에서 Harness 구현과 분석을 진행
- SCPC 공개 개발셋에서 규칙을 반복 개선한 기록
- 공개 개발셋 결과와 숨은 데이터의 일반화 성능을 동일시하면 안 된다는 판단

### B등급: 본인이 확인한 뒤 사용

프로젝트와 정황은 있으나, 현재 자료만으로 개인 역할이나 완료 상태가 확정되지 않는 내용이다.

- 동국대학교 전자전기공학부 재학과 현재 학적
- DanceOrFreeze에서 본인이 직접 작성한 코드와 설계 범위
- DanceOrFreeze의 특정 기능을 본인이 최초로 결정했는지 여부
- GitHub Issue와 Branch 정리를 본인이 주도했는지 여부
- OneThing의 현재 App Store 심사·출시 상태
- APEX 프로젝트의 정확한 구성과 본인 역할

- ChatGPT와 Gemini를 사용한 구체적인 사례
- 영어 협업 가능 수준
- 전체 해커톤 참가 횟수
- Junction을 알게 된 실제 경로

B등급 내용은 다음 질문에 모두 `예`라고 답할 수 있을 때만 사용한다.

- 내가 직접 경험한 사실인가?
- 다른 사람이 물으면 날짜·상황·행동을 설명할 수 있는가?
- 내 역할과 팀의 역할을 구분할 수 있는가?
- 결과물이나 기록을 보여줄 수 있는가?

### C등급: 확인 전 사용 금지

질문지 생성 과정에서 ChatGPT가 채운 것으로 보이거나 기존 기록과 충돌하는 내용이다.

- 아버지가 소방관이라는 주장
- 아버지를 통해 현장 정보를 직접 들었다는 주장
- 본인이 현직 소방관을 직접 인터뷰했다는 주장
- 휴대전화·Apple Watch 사용 실태를 직접 검증했다는 주장
- OneThing이 App Store에 최종 출시됐다는 주장
- Reddit에서 AI 사용과 C/C++ 대체에 관한 구체적인 비판을 받았다는 주장
- APEX에서 14개 복도 구간과 200개 이상의 LED를 제어했다는 정확한 수치
- Apple Watch 중심으로 RIT 프로젝트 전체 구조를 변경했다는 주장
- RIT MVP의 타이머가 5·10·15·20분이라는 주장
- SCPC에서 일반적인 Agent의 Tool 호출·재시도·비용 관리 전체를 설계했다는 주장

본인이 실제 사실임을 기억하고 증명할 수 있다면 C등급을 B등급으로 올릴 수 있다. 그렇지 않으면 지원서에서 완전히 제외한다.

## 4. 경험 배치 원칙

한 프로젝트를 모든 문항에서 반복하지 않는다. 각 경험이 다른 역량을 증명하도록 배치한다.

| 경험 | 가장 적합한 문항 | 증명할 역량 |
| --- | --- | --- |
| DanceOrFreeze | 1번, 3-1번 | 팀 개발, 다중 디바이스 통합, 실제 구현 |
| Embedded-Swift-Xcode-Template | 1번, 4번, 5번 | 끈기, 낯선 기술 탐색, 재현성, 공개 검증 |
| RIT 커맨드보드 | 1번 또는 5번 | 문제 정의, 안전한 표현, 가정과 사실의 분리 |
| SCPC AI Challenge | 1번 또는 5번 | AI 결과 검증, 평가 구조 이해, 일반화 경계 |
| OneThing | 사실 확인 후 보조 사례 | 제품 마감, 실제 기기·배포 준비 |

### 반복 제한

- 같은 프로젝트를 긴 문단으로 두 번 이상 설명하지 않는다.
- 1번에서는 프로젝트를 한두 문장으로 소개한다.
- 3-1번에서는 DanceOrFreeze의 기술 구조와 본인의 팀 기여를 구체적으로 설명한다.
- 4번에서는 Embedded Swift 경험 하나에 집중한다.
- 5번에서는 AI 사용 방식만 설명하고 프로젝트 자체를 다시 길게 소개하지 않는다.

## 5. 문항별 작성 명세

# 문항 1. 간단한 자기소개

## 이 문항의 역할

심사자가 나머지 답변을 읽기 전에 다음을 빠르게 이해하게 해야 한다.

- 현재 무엇을 배우고 있는가
- 어떤 종류의 개발자인가
- 어떤 결과물을 만든 경험이 있는가
- 팀에 어떤 강점을 가져오는가

## 권장 분량

- 650~850자
- 4~6개 문단 또는 하나의 긴 문단
- 프로젝트는 최대 3개까지만 언급

## 반드시 포함할 내용

### 1. 현재 정체성

다음 중 사실인 것을 본인의 표현으로 쓴다.

- Apple Developer Academy @ POSTECH Learner
- 전자전기공학 기반
- iOS·SwiftUI와 임베디드 시스템을 함께 다룸

학교와 학적을 넣을 경우 직접 확인한다.

### 2. 기술적 방향성

기술 목록만 나열하지 말고 연결점을 설명한다.

권장 방향:

> 앱, 무선 통신과 물리적 디바이스를 사용자가 경험하는 하나의 시스템으로 연결하는 데 관심이 있다.

### 3. 확인 가능한 대표 결과

두 개 정도 선택한다.

- DanceOrFreeze 팀 프로젝트
- Embedded-Swift-Xcode-Template 공개
- RIT 커맨드보드 진행
- SCPC AI Challenge 진행

가장 권장하는 조합:

1. DanceOrFreeze: 팀과 실제 시스템을 구현한 경험
2. Embedded Swift Template: 개인적으로 파고들어 공개한 경험
3. RIT 또는 SCPC: 현재 관심사를 짧게 보완

### 4. 팀에서의 역할

다음 중 실제 자신과 가까운 내용을 선택한다.

- 아이디어를 데이터 흐름과 구현 단위로 나눈다.
- 앱과 하드웨어의 연결 지점을 찾는다.
- 가장 위험한 가설을 작은 실험으로 먼저 확인한다.
- 개별 기능을 End-to-End 흐름으로 연결한다.
- 기술적 가능성과 실제 필요성을 구분하려 한다.

## 선택적으로 포함할 내용

- 새로운 기술을 빠르게 학습하는 방식
- 사용자가 보는 경험과 실패 상태를 함께 고려한다는 태도
- AI를 사용하되 실행으로 검증한다는 원칙

## 빼야 할 내용

- Junction 지원 동기: 2번에서 설명
- 48시간 작업 계획: 3-1번에서 설명
- Embedded Swift의 상세 오류: 4번에서 설명
- AI 보안 원칙: 5번에서 설명
- 확인되지 않은 소방관 인터뷰
- GitHub Star 수를 자기소개 핵심으로 사용하는 것
- 모든 프로젝트와 기술을 한 번에 나열하는 것

## 작성 순서

```text
현재 신분
→ 기술적 관심의 연결점
→ 대표 경험 2~3개
→ 팀에서 발휘할 강점
```

## 자기검수 질문

- 첫 두 문장만 읽어도 어떤 개발자인지 알 수 있는가?
- 기술 이름보다 내가 만든 시스템이 보이는가?
- 팀 프로젝트를 혼자 만든 것처럼 표현하지 않았는가?
- 2번 지원 동기와 내용이 겹치지 않는가?

# 문항 2. 지원 동기, 목표와 해커톤의 의미

## 이 문항의 역할

다음 세 질문에 모두 답해야 한다.

1. 왜 해커톤인가?
2. 왜 JUNCTIONX Korea 2026인가?
3. 참여 후 무엇을 얻거나 증명하고 싶은가?

운영진에게 전하고 싶은 말은 필수가 아니다. 진짜 할 말이 있을 때만 넣는다.

## 권장 분량

- 750~950자
- 전체 문항 중 가장 개인적인 생각이 드러나야 함

## 반드시 포함할 내용

### 1. 나에게 해커톤이란 무엇인가

단순히 “짧은 시간에 협업하는 행사”라고 정의하지 않는다.

현재 경험과 연결되는 권장 방향:

> 불확실한 문제에서 가장 중요한 가설을 선택하고, 팀과 작동하는 증거를 만드는 압축된 제품 실험

이 문구를 그대로 사용할 필요는 없다. 본인의 말로 바꾼다.

### 2. 현재 자신의 강점과 개선하고 싶은 점

강점만 쓰지 않는다. Junction이 왜 지금 필요한지 설명하려면 개선하고 싶은 부분이 있어야 한다.

사용 가능한 강점:

- 숨은 기술 조건을 찾는다.
- 시스템 전체를 구조화한다.
- 앱과 하드웨어를 연결한다.
- 직접 실행하고 검증한다.

사용 가능한 개선점:

- 충분한 근거를 찾으려 결정을 늦출 수 있다.
- 기술적 가능성이 보이면 범위를 넓힐 수 있다.
- 설명이 길어질 수 있다.
- 복잡한 구조를 먼저 생각할 수 있다.

개선점은 자기비하가 아니라 Junction에서 훈련하고 싶은 능력으로 연결한다.

### 3. Junction의 특성과 연결

공식적으로 확인된 요소만 사용한다.

- 48시간
- 트랙은 행사 초반 공개
- 개발자·디자이너·기획자의 협업
- 트랙 파트너 워크숍과 피드백
- Demo Expo와 Final Pitch
- BREAK, REBUILD, IMAGINE

세 가치의 뜻을 모두 설명할 필요는 없다. 본인과 가장 가까운 하나 또는 두 개를 선택해도 된다.

권장 방식:

- BREAK: 익숙한 기술과 최초 가정을 의심함
- REBUILD: 다른 역할의 팀원과 문제를 다시 구성함
- IMAGINE: 가능성을 작동하는 프로토타입으로 보여줌

### 4. 구체적인 목표

목표는 최소 세 종류가 들어가야 한다.

- 제품 목표:
  - 한 가지 핵심 가치가 End-to-End로 동작하는 MVP
- 협업 목표:
  - 다른 직군의 판단 방식을 배우고 같은 문제 정의에 합의
- 개인 성장 목표:
  - 불확실성이 남아 있어도 시간 안에 결정하고 완성
- 발표 목표:
  - 기술 목록이 아니라 사용자의 변화를 보여주는 데모

```text
→ 공식 문서·소스에서 존재 여부 확인
→ 최소 예제 Build
→ Log 확인
→ 실제 Device·Hardware Test
→ 반복 재현
```

### 6. 보안 원칙

짧게 포함한다.

- API Key, Token과 Password를 입력하지 않음
- 실제 개인정보를 익명화
- 비공개 자료 전체 대신 필요한 최소 구조만 제공
- Mock Data 사용

## 선택적으로 포함할 내용

- AI가 틀린 답을 준 실제 사례
- AI 사용 전후에 달라진 학습 방식
- 팀원이 AI 사용을 꺼릴 때 합의할 방식
- 해커톤에서 AI를 사용할 단계별 계획

실제 사례가 기억나지 않으면 구체적인 허위 API 이름을 만들지 않는다.

## 빼야 할 내용

- AI가 거의 모든 코드를 작성해 준다는 인상
- “AI를 잘 활용해서 개발 속도가 몇 배 빨라졌다”는 근거 없는 수치
- 특정 허위 API나 라이브러리 사례
- AI는 항상 공식 문서로 검증한다고 하면서 실제 과정은 없는 문장
- SCPC의 역할을 일반적인 Agent Tool 설계로 과장
- AI 사용을 숨기거나 반대로 과도하게 방어하는 태도
- 개인정보를 절대 입력한 적 없다고 기억 없이 단정

## 작성 순서

```text
사용 도구와 목적
→ 대표 프로젝트의 실제 사용 과정
→ AI에 맡기지 않는 판단
→ 검증 방법
→ 보안 원칙
→ AI에 대한 최종 관점
```

## 자기검수 질문

- 도구 이름보다 실제 사용 과정이 더 많이 보이는가?
- AI가 틀릴 수 있다는 말을 구체적인 검증 행동으로 증명했는가?
- AI가 한 일과 내가 한 일을 구분했는가?
- README의 AI 활용 공개와 모순되지 않는가?
- 책임을 진다는 말이 실제 행동으로 연결되는가?

## 9. 제출 전 최종 자가검수표

- [ ] 직접 하지 않은 인터뷰를 했다고 쓰지 않았다.

- [ ] GitHub와 공개 링크가 실제로 열린다.

- [ ] 1번만 읽어도 어떤 개발자인지 알 수 있다.

## 10. 직접 작성할 때의 권장 작업 순서

1. 4번부터 작성한다.
   - 가장 구체적인 경험이라 본인의 문체를 잡기 쉽다.
2. 3-1번을 작성한다.
   - 과거 경험을 Junction 팀의 미래 행동으로 바꾼다.
3. 1번을 작성한다.
   - 앞에서 드러난 특징을 압축해 자기소개로 만든다.
4. 5번을 작성한다.
   - 실제 AI 사용과 검증만 분리해 쓴다.
5. 2번을 마지막으로 작성한다.
   - 전체 경험을 바탕으로 왜 Junction이 필요한지 연결한다.
6. 6·7번을 사실대로 짧게 작성한다.
7. 각 문항에서 가장 `AI가 쓴 것 같은 문장` 한 개씩을 찾아 본인의 말로 다시 쓴다.
8. 하루 또는 최소 30분 뒤 다시 읽고 반복 문장을 제거한다.
9. 가능하면 소리 내어 읽는다.
   - 입으로 말하기 어려운 문장은 지원서에서도 부자연스러울 가능성이 높다.
10. 최종 글자 수와 사실 여부를 확인한다.
