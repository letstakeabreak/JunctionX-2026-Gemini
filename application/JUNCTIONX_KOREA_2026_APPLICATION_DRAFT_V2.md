### 제출용 답변

안녕하세요. Apple Developer Academy @ POSTECH에서 iOS와 제품 개발을 배우고 있는 고기범입니다. 전자전기공학과 임베디드 시스템에서 출발해 현재는 SwiftUI 앱, ESP32 기반 디바이스, BLE·ESP-NOW 통신을 하나의 제품 경험으로 연결하는 작업에 관심을 두고 있습니다. Apple Developer Academy의 DanceOrFreeze 프로젝트에서는 iPad 앱과 고정형 ESP32-C6 Hub, 여러 웨어러블 디바이스가 BLE와 ESP-NOW로 명령과 움직임 데이터를 주고받는 시스템을 팀과 구현했습니다. 개인적으로는 Xcode에서 Embedded Swift 펌웨어를 빌드하고 ESP32-C6에 플래시할 수 있는 템플릿과 설치 도구를 만들어 오픈소스로 공개했습니다. 최근에는 소방 현장의 퇴출 명령, 응답, 연결과 복귀 상태를 지휘관이 구분해 볼 수 있는 iPad 기반 RIT 커맨드보드를 기획하고 있습니다. SCPC AI Challenge에서는 복잡한 대화 맥락과 안전 정책을 일관된 실행 판단으로 바꾸는 Agent Harness를 분석하며, 자연스러운 AI 답변과 검증 가능한 시스템 동작은 다르다는 점을 배웠습니다. 저는 기술부터 고르기보다 사용자의 핵심 행동과 실패 조건을 먼저 정리하고, 가장 위험한 가정을 작은 실험으로 확인하는 편입니다. 화면 안의 앱과 화면 밖의 디바이스를 따로 보지 않고 사용자가 겪는 하나의 흐름으로 보려 합니다. 팀에서는 추상적인 아이디어를 데이터 흐름과 구현 단위로 나누고, 개별 기능을 처음부터 끝까지 작동하는 경험으로 연결하는 개발자가 되고자 합니다.

## 2. 지원 동기, 목표, 나에게 해커톤이란

### 제출용 답변

저에게 해커톤은 많은 기능을 빠르게 만드는 행사가 아니라, 불확실한 문제에서 가장 중요한 가설을 선택하고 팀과 작동하는 증거를 만드는 압축된 제품 실험입니다. 프로젝트를 진행하며 저는 숨은 기술 조건을 찾고 시스템 전체를 구조화하는 데 강점이 있는 반면, 충분한 근거를 찾으려 결정을 늦추거나 구현 가능성이 보이면 범위를 넓히는 경향도 발견했습니다. 그래서 낯선 트랙과 처음 만난 팀, 48시간이라는 제한이 있는 JUNCTIONX Korea 2026에서 깊게 사고하면서도 필요한 순간에 결정을 내리는 능력을 시험하고 싶습니다. 특히 익숙한 해결책을 의심하는 BREAK, 서로 다른 사람과 기술을 다시 연결하는 REBUILD, 아직 없는 경험을 프로토타입으로 보여주는 IMAGINE이라는 가치가 제가 제품을 만드는 방식과 맞닿아 있습니다. SwiftUI, BLE, ESP32와 AI 도구 활용 경험을 기여하되, 익숙한 기술을 억지로 사용하지 않고 문제에 필요한 방법을 선택하겠습니다. 첫째, 초반에는 핵심 사용자의 문제와 가장 위험한 가설을 팀의 언어로 합의하겠습니다. 둘째, 중간에는 처음부터 끝까지 실제로 동작하는 최소 흐름을 만들고 트랙 파트너의 피드백을 반영하겠습니다. 셋째, 마지막에는 기술을 나열하는 발표가 아니라 사용자의 변화가 보이는 데모를 완성하겠습니다. 다른 배경의 개발자·디자이너·기획자가 같은 문제를 다르게 해석하는 과정에서 제 판단의 맹점도 발견하고 싶습니다. 구현한 것과 아직 가정인 것을 솔직히 구분하고, 48시간의 선택과 실패에서 다음 실험까지 도출한다면 수상과 별개로 성공한 해커톤이라고 생각합니다.

## 3-1. 맡고 싶은 역할과 기여 방식

### 제출용 답변

팀의 아이디어를 검증 가능한 시스템으로 바꾸는 Developer 역할을 맡고 싶습니다. SwiftUI 기반 iPad 앱과 ESP32-C6 디바이스를 BLE·ESP-NOW로 연결한 경험이 있어, 센서 입력과 무선 통신부터 상태 처리, 화면과 물리적 피드백까지 이어지는 프로토타입에 기여할 수 있습니다. DanceOrFreeze에서는 iPad를 BLE Central, 고정형 ESP32-C6를 Peripheral이자 ESP-NOW Hub로 두고 여러 참가자 디바이스에 명령을 전달한 뒤 움직임과 상태를 앱으로 돌려보내는 구조를 팀과 구현했습니다. 이 경험을 바탕으로 해커톤 초반에는 아이디어를 사용자 행동, 입력, 처리와 피드백으로 나누고 프로젝트를 무너뜨릴 기술 가설부터 확인하겠습니다. BLE가 핵심이면 화면보다 데이터 한 줄의 왕복부터, 센서가 핵심이면 실제 값의 분포부터 시험하겠습니다. 핵심 기술이 성립하면 임시 UI와 Mock Data를 사용해서라도 최소 End-to-End 흐름을 먼저 연결하고, 후반에는 기능 추가보다 통합과 데모 안정화에 집중하겠습니다. 기획자와 디자이너에게 기술적 제약만 전달하지 않고 가능한 범위와 대안을 함께 설명하며, 다른 개발자와는 모듈의 입력·출력과 완료 조건을 먼저 합의하겠습니다. 예상보다 개발이 늦어지면 핵심 사용 흐름을 남기고 자동화를 수동 확인으로 바꾸거나 기기 수를 줄이는 등 대체 경로를 제안하겠습니다. 발표 전에는 실제 기기에서 같은 시나리오를 반복 실행하고, 외부 API나 통신이 실패해도 핵심 가치를 설명할 수 있는 백업 데모를 준비하겠습니다. 필요한 기술을 선택하고 팀의 핵심 가설을 실제 작동하는 결과로 끝까지 증명하는 것이 제 기여 방식입니다.

## 4. 끝까지 파고든 경험과 성장

### 제출용 답변

Swift와 Xcode를 사용해 ESP32-C6 펌웨어를 개발할 수 있는 Embedded-Swift-Xcode-Template을 만든 경험이 있습니다. 처음에는 기존 예제와 플래시 도구를 연결하면 빠르게 끝날 것이라 생각했지만, 컴파일 성공, 펌웨어 생성, 보드 플래시와 실제 실행은 서로 다른 성공 조건이었습니다. 빌드가 끝났는데 보드가 기대대로 동작하지 않으면 원인이 Swift 코드, 툴체인, 경로, 플래시 과정과 하드웨어 중 어디에 있는지부터 나눠야 했습니다. 저는 전체 설정을 한꺼번에 바꾸는 대신 Compile-Artifact-Flash-Boot-Output 단계로 분해하고, Xcode에서 빌드한 뒤 실제 보드의 NeoPixel이 반복해서 동작하는지 확인했습니다. 이후 이 흐름을 프로젝트 템플릿, 자동 플래시 스크립트, Serial Monitor와 SwiftUI 설치 도구로 정리해 GitHub에 공개했습니다. 프로젝트가 아직 Experimental Preview라는 한계와 검증 환경도 문서에 명시했습니다. 공개 후 Swift Forums의 다른 개발자가 자신의 ESP32-C6 DevKit에서 LED 동작을 재현했고, 자동 생성되지 않는 디렉터리와 하드코딩된 변수 문제를 알려주었습니다. 이 경험을 통해 끝까지 파고든다는 것은 오류를 오래 붙잡는 것이 아니라 문제를 검증 가능한 단계로 나누고, 내 환경의 한 번의 성공을 다른 사람이 재현할 수 있는 결과로 바꾸는 일임을 배웠습니다. 또한 완성도를 과장하지 않고 확인한 범위와 남은 한계를 함께 공개하는 것이 개발자의 책임임을 배웠습니다.

## 5. 개발 시 AI 도구 활용 방식

### 제출용 답변

ChatGPT, Codex, Claude와 Gemini를 기술 탐색, 오류 원인 후보 생성, 코드·문서 초안과 테스트 케이스 작성에 활용합니다. 다만 AI 사용의 핵심은 얼마나 많은 코드를 생성했는지가 아니라, 생성된 결과를 실제 환경에서 검증하고 최종 판단을 책임지는 것이라고 생각합니다. Embedded-Swift-Xcode-Template에서는 Claude의 도움을 받아 빌드 구조와 스크립트 후보를 탐색했지만, 아키텍처 선택, 디버깅과 하드웨어 검증은 직접 수행했으며 이 사실을 README에도 공개했습니다. AI가 제안한 API나 옵션이 현재 툴체인에 실제로 존재하는지 공식 문서와 소스에서 확인하고, 최소 예제로 빌드한 뒤 펌웨어 생성, 보드 플래시와 실제 출력을 순서대로 시험했습니다. SCPC AI Challenge에서는 Codex와 함께 공개 개발 과제를 비교하는 분석 도구와 Harness 규칙을 만들었지만, 같은 개발셋 점수의 상승을 숨은 과제에 대한 일반화 성능으로 과장하지 않고 별도의 위험으로 기록했습니다. 소방 현장 프로젝트에서는 AI로 아이디어와 요구사항을 확장하되, 공개 데이터에 없는 위험정보를 추정하거나 소비자용 기기를 인증 안전장비처럼 표현하지 않도록 가정과 검증된 사실을 분리했습니다. AI에는 탐색, 반복 작업과 대안 생성을 맡기지만, 문제 정의, 아키텍처, 우선순위, 개인정보·보안과 배포 여부는 제가 판단합니다. API Key, 개인정보와 비공개 자료는 입력하지 않고 필요한 구조만 익명화해 제공합니다. AI가 답을 만든 순간이 아니라, 그 답이 왜 맞거나 틀렸는지 설명하고 실제 실행으로 재현할 수 있을 때 작업이 완료됐다고 봅니다.
